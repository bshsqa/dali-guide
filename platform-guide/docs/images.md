## Introduction to the DALi Image Subsystem

The DALi Image Subsystem serves as the foundation for all visual content within the engine, providing a unified interface for handling raw pixel buffers and platform-specific image resources. It abstracts the complexities of memory allocation and format conversion, allowing developers to efficiently prepare image data for the GPU-based [rendering](./rendering.md) pipeline.

By utilizing this subsystem, developers gain the ability to manage image data lifecycle independently of the scene graph. It is distinct from higher-level visual components because it focuses exclusively on the representation and preparation of pixel data before it is mapped onto actors or textures.

## Pixel Data Management

The `PixelData` class is the primary mechanism for encapsulating raw pixel buffers, their dimensions, and their underlying format. It acts as a memory container that the engine can safely upload to the GPU or share with hardware-accelerated image decoders.

### Using PixelData

`PixelData` should be utilized whenever you need to pass raw memory blocks, such as those generated by a custom software decoder or a captured frame, into the DALi engine. 

> **Note:** `PixelData` does not perform image file format decoding (e.g., JPEG/PNG); it expects a pre-allocated buffer of raw bytes consistent with the specified `Pixel::Format`.

```cpp
#include <dali/dali.h>

// Example: Creating a raw PixelData object
void CreateRawImage() {
    uint32_t width = 256;
    uint32_t height = 256;
    unsigned char* buffer = new unsigned char[width * height * 4];
    
    // Create the PixelData object taking ownership of the buffer
    Dali::PixelData pixelData = Dali::PixelData::New(
        buffer, 
        width * height * 4, 
        width, 
        height, 
        Dali::Pixel::RGBA8888, 
        Dali::PixelData::FREE
    );
}
```

## Pixel Format Specifications

The `Dali::Pixel` namespace defines the available pixel formats and internal memory layouts required to communicate with the graphics backend. Selecting the correct format is critical for both visual accuracy and memory efficiency.

### Understanding Pixel Formats

The engine supports various formats, ranging from standard 32-bit RGBA to compressed formats designed to minimize memory footprint. When configuring your `PixelData`, ensure the format matches the layout of your raw source buffer exactly to prevent memory corruption or display artifacts.

> **Warning:** Using an incorrect `Pixel::Format` enum will result in distorted rendering or, in severe cases, driver-level errors during texture uploads.

## Native Image Integration

The `NativeImageInterface` provides an abstraction layer to bridge platform-specific graphics buffers (such as EGLImage or other system-level textures) with the DALi rendering pipeline.

### Implementing NativeImageInterface

This interface is intended for advanced use cases where you need to display surfaces generated by external hardware components, such as camera streams or hardware-decoded video buffers. By implementing this interface, you can provide the engine with a direct pointer or handle to platform-specific memory, avoiding costly CPU-to-GPU copies.

→ See: [Internal Lifecycle and Threading]

## Distance Field Generation and Usage

Distance fields provide a robust method for rendering high-quality vector graphics and fonts at any scale. Instead of storing explicit pixel color data, this utility generates a map representing the distance to the nearest boundary of the graphical element.

### Generating Distance Fields

The distance field utility is typically used during asset preparation. When rendering, a shader samples this field to determine the anti-aliased edge of the shape, allowing for sharp rendering regardless of the zoom level or transformation applied to the parent actor.

## Internal Lifecycle and Threading

Effective management of image data requires a strict understanding of thread affinity within the DALi engine. 

### Thread Safety Guidelines

While the `PixelData` objects are handle-based and can be passed between threads, the underlying raw buffers should only be modified by the thread that owns them. Once a `PixelData` object is passed to the engine for rendering (via a visual or texture), it must be treated as immutable by the application to avoid race conditions with the render-side upload processes.

> **Note:** Always ensure that any memory buffers passed to `PixelData` with the `Dali::PixelData::FREE` flag are allocated using standard heap allocation (malloc/new) to avoid heap corruption during the engine's internal deallocation phase.

## Integration API Best Practices

The Integration API allows for low-level interaction with the DALi render graph, enabling the direct injection of image buffers into the rendering process.

### Direct Render Graph Integration

When integrating low-level buffers, developers should favor the `NativeImageInterface` for zero-copy operations. If you are creating custom rendering effects that involve pixel manipulation, perform these on a background thread and signal the main thread to perform the texture update only once the buffer is ready for use. This maintains the responsiveness of the UI and prevents dropped frames during image updates.

```cpp
// Advanced Usage: Ensuring UI responsiveness during image buffer updates
void UpdateImageAsync(Dali::Actor actor, Dali::PixelData newData) {
    // Perform processing off-thread, then update on the main thread
    Dali::CustomEvent::Post([=]() {
        // Apply the new PixelData to a visual component or shader property here
        // ... implementation dependent on render graph state
    });
}
```
