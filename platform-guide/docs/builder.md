## Introduction to the Builder Module

The `Dali::Ui::Builder` module serves as the primary declarative engine within the DALi framework, enabling developers to construct complex UI hierarchies and define animations from externalized data sources such as JSON files. It bridges the gap between static design definitions and the dynamic C++ scene graph, allowing for rapid UI iteration without requiring full recompilation of the application logic.

Unlike manual scene graph construction, the Builder is distinct in its ability to parse hierarchical structures, manage stateful constants, and apply modular style templates to existing actor objects. Use the Builder when your application requires a data-driven UI, theme-able components, or the separation of layout logic from functional implementation.

## Architecture and Internal Data Flow

The Builder functions as an interpretation layer that consumes structured data and transforms it into live DALi handles. It coordinates the conversion of raw strings or files into an intermediate tree representation before performing the semantic binding required to materialize UI objects.

### Object Instantiation Process
The engine internalizes data via `LoadFromString`, which populates an internal registry. Subsequent calls to `Create()` or `CreateFromJson()` trigger a traversal of this registry, mapping requested identifiers to specific DALi [object](./object.md) constructors and property values.

## JSON Parsing and Tree Traversal

The Builder relies on a robust parsing mechanism to transform raw JSON [text](./text.md) into an actionable [object](./object.md) graph. While the `Dali::Ui::TreeNode` structure serves as the underlying representation, the `Builder` abstracts this navigation for the end developer through high-level creation APIs.

### Navigating the Tree
Internal nodes are navigated using the `ConstIterator`, which provides standard forward-iterator semantics for traversing the [object](./object.md) hierarchy generated by the parser.

```cpp
// Example: Basic initialization and parsing
Dali::Ui::Builder builder = Dali::Ui::Builder::New();
std::string json = "{\"templates\":{\"myActor\":{\"type\":\"Actor\"}}}";
builder.LoadFromString(json);

// The builder now holds a reference to the 'myActor' template defined in the JSON.
```

> Note: Accessing the `TreeNode` structure directly is typically reserved for internal diagnostic tools. For standard application development, use the `Create` methods to instantiate objects.

## Builder Lifecycle and Threading Constraints

The `Dali::Ui::Builder` instance must be managed carefully within the application lifecycle. Because the Builder interacts directly with the DALi scene graph, all methods must be invoked on the main (UI) thread to avoid race conditions or undefined behavior during object creation and attachment.

### Initialization and Cleanup
* **Initialization**: Instantiate via `Dali::Ui::Builder::New()`.
* **Execution**: Load definitions early in the application startup or component initialization phase.
* **Cleanup**: The destructor `~Builder()` automatically releases internal references to generated objects; however, any objects already added to the scene graph remain until their respective parent actors are destroyed.

## Managing the UI Object Graph

The Builder excels at creating complex UI snapshots and re-applying them to existing hierarchies. It differentiates between creating new objects and modifying existing ones via style applications.

### Creating and Applying Styles
* **Create()**: Generates a `BaseHandle` (e.g., an `Actor`) from a pre-defined template.
* **ApplyStyle()**: Attempts to update an existing `Handle` with properties defined in a specific style block.

```cpp
Dali::Ui::Builder builder = Dali::Ui::Builder::New();
builder.LoadFromString(json_data);

// Create an object from a template
Dali::BaseHandle handle = builder.Create("myTemplateName");
Dali::Actor actor = Dali::Actor::DownCast(handle);

// Apply a specific style to an existing actor
bool success = builder.ApplyStyle("myStyleName", actor);
```

## Integration API Usage Patterns

The integration APIs allow for dynamic injection of runtime data into the build process, enabling variable-driven layouts and dynamic animations.

### Handling Constants and Configurations
The `AddConstant` and `AddConstants` methods allow you to inject `Property::Map` data that will be substituted into templates during the creation phase.

```cpp
Dali::Ui::Builder builder = Dali::Ui::Builder::New();

// Inject dynamic color or layout values
Dali::Property::Map myConstants;
myConstants.Insert("themeColor", Dali::Property::Value(Dali::Vector4(1, 0, 0, 1)));
builder.AddConstants(myConstants);

// Create an animation using these constants
Dali::Animation anim = builder.CreateAnimation("FadeAnimation", myConstants);
anim.Play();
```

> Warning: Constants must be added *before* the `Create` or `CreateAnimation` call to ensure the engine correctly resolves the template expressions.

## Error Handling and Debugging

When the Builder encounters malformed data or missing references, it returns default handles or returns `false` in boolean-returning methods. 

### Diagnostic Patterns
* **Return Value Checks**: Always verify the result of `ApplyStyle` and `ApplyFromJson`.
* **Invalid Constants**: Use `GetConstant(key)` to verify that a value exists before attempting to use it; it returns `Property::INVALID` if the key is missing.
* **QuitSignal**: Monitor `QuitSignal()` to detect if the builder configuration contains an explicit "quit" directive, which is useful for debugging automated UI test suites or application exit flows.

```cpp
// Example: Checking for proper constant resolution
const Dali::Property::Value& val = builder.GetConstant("requiredKey");
if(val == Dali::Property::INVALID) {
  // Log error: missing constant
}
```
