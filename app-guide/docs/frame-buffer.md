## Introduction to [FrameBuffer](./frame-buffer.md)

A `FrameBuffer` is an off-screen [rendering](./rendering.md) target that allows you to capture [rendering](./rendering.md) commands into a texture instead of directly onto the display surface. You should use a `FrameBuffer` when you need to perform post-processing, create complex multi-pass [rendering](./rendering.md) effects, or generate dynamic content that must be reused as an input texture for other actors in your scene.

Unlike standard screen [rendering](./rendering.md), `FrameBuffer` provides the flexibility to isolate geometry or effects into a texture that acts as a persistent resource. This is distinct from standard scene graph [rendering](./rendering.md) because it decouples the content generation from the final display output, enabling techniques like reflection mapping, blur filters, or UI element caching.

## Creating and Configuring FrameBuffers

Instantiating a `FrameBuffer` involves defining the dimensions and attachment requirements for your off-screen surface. By specifying the `Attachment::Mask`, you control whether the buffer manages depth or color storage automatically.

### Instantiating the [FrameBuffer](./frame-buffer.md)
The `New` static methods serve as the factory for creating `FrameBuffer` objects. You can either let the framework create a default color-only buffer or specify custom attachments for more complex [rendering](./rendering.md) requirements.

**Example: Creating a standard [FrameBuffer](./frame-buffer.md)**
```cpp
#include <dali/public-api/rendering/frame-buffer.h>

// Create a FrameBuffer of 512x512 pixels
uint32_t width = 512;
uint32_t height = 512;
Dali::FrameBuffer myFrameBuffer = Dali::FrameBuffer::New(width, height);
```

> Note: If your rendering pipeline requires specific depth or stencil support beyond the default configuration, ensure you use the `Attachment::Mask` constructor, which is a platform-level detail (see the platform guide for mask definitions).

## Managing Color Textures

`[FrameBuffer](./frame-buffer.md)` objects do not hold visual data themselves; they act as containers for `Texture` objects. By attaching a texture, you define the memory destination for the GPU's color output.

### Attaching and Retrieving Textures
Use `AttachColorTexture` to bind a specific `Texture` instance to the `[FrameBuffer](./frame-buffer.md)`. If you need to access the rendering result later—for example, to display the captured buffer on a `MeshVisual` or `ImageActor`—use `GetColorTexture`.

**Example: Binding a custom texture to a FrameBuffer**
```cpp
#include <dali/public-api/rendering/frame-buffer.h>
#include <dali/public-api/rendering/texture.h>

// Assuming 'myTexture' is a valid, pre-allocated Texture object
void SetupFrameBuffer(Dali::FrameBuffer& buffer, Dali::Texture& texture)
{
  // Attach the base LOD (Level of Detail) of the texture
  buffer.AttachColorTexture(texture);
  
  // Alternatively, attach a specific mipmap and layer
  // buffer.AttachColorTexture(texture, 0, 0);
}

// Retrieve the texture to display it elsewhere
Dali::Texture result = myFrameBuffer.GetColorTexture();
```

## Practical Usage Patterns

The `[FrameBuffer](./frame-buffer.md)` is a foundational component for creating dynamic visual effects. Common patterns include rendering a 3D scene to a texture for a "portal" effect or creating a reflection map by rendering a scene from an inverted camera perspective into a texture.

### Implementing a Rendering Overlay
To use the rendered result, you retrieve the texture from the `[FrameBuffer](./frame-buffer.md)` and apply it to a material or visual. This allows you to treat the output of one render pass as the input for another, enabling multi-pass pipelines.

**Example: Creating a dynamic texture overlay**
```cpp
// 1. Create the buffer
Dali::FrameBuffer fb = Dali::FrameBuffer::New(1024, 1024);

// 2. Retrieve the color texture generated by the buffer
Dali::Texture capturedTexture = fb.GetColorTexture();

// 3. Use 'capturedTexture' in an actor's material
// (Refer to Rendering docs for applying textures to Actors)
```

→ See: [Texture]

## FrameBuffer Best Practices

Efficiency is critical when using off-screen buffers, as they consume GPU memory and require additional draw passes. Following these guidelines will help maintain application performance:

*   **Size Constraints:** Match your `[FrameBuffer](./frame-buffer.md)` dimensions closely to the required display area. Using excessively large buffers increases fill-rate overhead and VRAM usage.
*   **Reuse:** Avoid creating and destroying `[FrameBuffer](./frame-buffer.md)` objects every frame. Create them once during object initialization and reuse them throughout the lifecycle of the visual effect.
*   **Handle Management:** `[FrameBuffer](./frame-buffer.md)` uses handle-based memory management. While copying and moving handles is inexpensive, ensure you are not leaking references if you are dynamically generating many buffers.

> Warning: Frequent switching between different `[FrameBuffer](./frame-buffer.md)` targets during a single frame can lead to pipeline stalls on some hardware. Minimize state changes to optimize [rendering](./rendering.md) throughput.
